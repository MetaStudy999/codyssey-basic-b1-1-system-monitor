# 01. 실습 환경 준비와 사전 점검

> 이 장의 목적은 **시스템 설정을 바꾸기 전에 현재 환경이 미션을 수행할 준비가 되었는지 확인하는 것**입니다.  
> 대부분의 명령은 조회용입니다. `[GO]` 조건을 확인하기 전에는 다음 단계로 넘어가지 않습니다.

## 1. 이번 장에서 하는 일

이 장에서는 다음 내용을 하나씩 확인합니다.

1. 지금 어떤 사용자로 로그인했는지 확인합니다.
2. 현재 작업 위치를 확인합니다.
3. Ubuntu 버전을 확인합니다.
4. CPU 아키텍처를 확인합니다.
5. `systemd`를 사용할 수 있는지 확인합니다.
6. `sudo` 관리자 권한을 사용할 수 있는지 확인합니다.
7. SSH, UFW, cron, ACL, `ss`, logrotate 도구가 준비되어 있는지 확인합니다.
8. 현재 IP 주소와 주요 포트 사용 상태를 확인합니다.
9. 디스크 여유 공간을 확인합니다.
10. 문제가 생겼을 때 되돌아올 수 있는 복구 수단을 확인합니다.

이 장이 끝나면 **SSH나 방화벽을 변경하기 전에 현재 서버 상태가 안전한지 판단할 수 있습니다.**

---

## 2. 왜 환경부터 확인하나요?

리눅스 명령은 운영체제 버전, 실행 계정, 서비스 관리자, 설치된 패키지에 따라 결과가 달라질 수 있습니다.

예를 들어 다음과 같은 차이가 있습니다.

- `sudo` 권한이 없으면 시스템 설정을 변경할 수 없습니다.
- `systemd`가 없으면 `systemctl` 명령으로 서비스를 관리할 수 없습니다.
- OpenSSH Server가 설치되어 있지 않으면 SSH 포트 변경을 진행할 수 없습니다.
- UFW가 설치되어 있지 않으면 방화벽 설정을 진행할 수 없습니다.
- ACL 도구가 없으면 `setfacl`, `getfacl`을 사용할 수 없습니다.

따라서 **먼저 확인하고, 부족한 항목만 보완한 뒤 다음 장으로 이동하는 방식**이 가장 안전합니다.

---

## 3. 기준 환경

원본 미션은 Ubuntu 22.04 또는 동등한 Linux 환경을 전제로 합니다. 이 저장소의 안내서는 Ubuntu LTS 계열에서 재현 가능하도록 작성하며, 현재 저장소의 기준 안내는 Ubuntu 24.04 LTS를 사용합니다.

```text
운영체제       : Ubuntu 24.04 LTS 기준
허용 범위      : Ubuntu 22.04 LTS 또는 동등 환경
CPU 아키텍처   : x86_64
서비스 관리자  : systemd
SSH            : OpenSSH Server
방화벽         : UFW
자동 실행      : cron
셸             : Bash
```

WSL2, OrbStack, Docker에서는 서비스와 네트워크 동작이 다를 수 있으므로 [환경별 차이](./reference/environment-differences.md)를 함께 확인합니다.

---

## 4. 시작 전 준비

### 실행 계정

이 장에서는 특별한 표시가 없는 한 **현재 Ubuntu에 로그인한 기존 sudo 사용자**로 실행합니다.

아직 `agent-admin`, `agent-dev`, `agent-test` 계정을 만들지 않습니다.

### 현재 위치

처음 몇 개의 조회 명령은 어느 디렉터리에서도 실행할 수 있습니다.

### 안전 규칙

- 한 번에 한 코드 블록만 실행합니다.
- 결과를 확인한 뒤 다음 명령으로 이동합니다.
- `[STOP]` 조건이 나오면 다음 명령을 실행하지 않습니다.
- 오류 메시지는 생략하지 않고 그대로 기록합니다.
- 이 장에서는 SSH 포트, 방화벽 규칙, 사용자, 파일 권한을 변경하지 않습니다.

---

# 5. 작업 1 — 현재 사용자 확인

## 무엇을 확인하나요?

현재 터미널에서 **어떤 사용자 계정으로 명령을 실행하고 있는지** 확인합니다.

리눅스에서는 사용자에 따라 파일 접근 권한과 실행 가능한 명령이 달라집니다. 이후 `sudo`를 사용하는 작업이 있으므로 현재 사용자를 먼저 알아야 합니다.

### 실행 계정

`[현재 sudo 사용자]`

### 실행 명령

```bash
whoami
```

### 명령어 뜻

`whoami`는 "나는 누구인가?"라는 의미로, 현재 로그인된 사용자 이름을 보여줍니다.

### 정상 출력 예시

```text
ubuntu
```

또는 사용자가 만든 다른 일반 계정 이름이 표시될 수 있습니다.

### `[CHECK]`

출력된 사용자 이름을 기억하거나 기록합니다.

### `[STOP]`

다음과 같이 `root`가 표시된다면 여기에서 잠시 멈춥니다.

```text
root
```

이 미션은 일반 사용자 기반 운영과 최소 권한 구성을 학습하는 것이 목적이므로, 처음부터 Root 계정으로 모든 작업을 진행하지 않습니다.

### `[GO]`

일반 사용자 이름이 정상적으로 출력되었습니다.

---

# 6. 작업 2 — 현재 작업 위치 확인

## 무엇을 확인하나요?

현재 터미널이 **어느 디렉터리를 바라보고 있는지** 확인합니다.

나중에는 파일을 생성하거나 저장소 안에서 명령을 실행하므로 현재 위치를 확인하는 습관이 중요합니다.

### 실행 명령

```bash
pwd
```

### 명령어 뜻

`pwd`는 **Print Working Directory**의 약자로, 현재 작업 중인 디렉터리의 전체 경로를 출력합니다.

### 정상 출력 예시

```text
/home/ubuntu
```

### `[CHECK]`

`/home/...` 형태의 경로가 보이면 정상입니다.

현재 위치가 예상과 달라도 이 단계에서는 문제가 아닙니다. 단지 위치를 확인하는 단계입니다.

### `[GO]`

현재 위치를 확인했습니다.

---

# 7. 작업 3 — Ubuntu 버전 확인

## 무엇을 확인하나요?

현재 운영체제가 Ubuntu인지, 어떤 버전인지 확인합니다.

운영체제 버전에 따라 패키지 버전과 서비스 동작이 조금씩 달라질 수 있으므로 반드시 기록합니다.

### 실행 명령

```bash
cat /etc/os-release
```

### 명령어 뜻

- `cat`: 파일 내용을 화면에 출력합니다.
- `/etc/os-release`: Linux 배포판 이름과 버전 정보가 저장된 표준 파일입니다.

### 정상 출력 예시

Ubuntu 24.04라면 다음과 비슷합니다.

```text
NAME="Ubuntu"
VERSION="24.04 LTS ..."
ID=ubuntu
VERSION_ID="24.04"
```

Ubuntu 22.04라면 `VERSION_ID="22.04"`처럼 표시됩니다.

### `[GO]`

다음 중 하나라면 계속 진행할 수 있습니다.

- Ubuntu 24.04 LTS
- Ubuntu 22.04 LTS
- 미션에서 동등 환경으로 인정되는 Ubuntu 계열 Linux

### `[STOP]`

다음 상황이면 바로 다음 단계로 가지 않습니다.

- Ubuntu가 아닌 환경인데 차이를 아직 확인하지 않음
- `/etc/os-release` 파일을 읽을 수 없음
- Docker 컨테이너처럼 `systemd`, SSH, UFW 실습이 제한될 가능성이 큼

환경이 다르면 [환경별 차이](./reference/environment-differences.md)를 먼저 확인합니다.

---

# 8. 작업 4 — CPU 아키텍처 확인

## 무엇을 확인하나요?

현재 시스템의 CPU 아키텍처를 확인합니다.

제공 프로그램이나 바이너리는 CPU 아키텍처에 따라 실행 가능 여부가 달라질 수 있습니다.

### 실행 명령

```bash
uname -m
```

### 명령어 뜻

`uname -m`은 현재 머신의 하드웨어 아키텍처를 출력합니다.

### 정상 출력 예시

```text
x86_64
```

### 다른 출력 예시

Apple Silicon 기반 Linux VM에서는 다음처럼 보일 수 있습니다.

```text
aarch64
```

### `[GO]`

`x86_64`라면 기준 환경과 일치합니다.

### `[STOP]`

`aarch64` 등 다른 아키텍처라면 제공 `agent-app`이 해당 아키텍처에서 실행 가능한지 확인하기 전에는 Agent 실행 단계로 넘어가지 않습니다.

---

# 9. 작업 5 — PID 1과 systemd 확인

## 무엇을 확인하나요?

Ubuntu가 서비스를 관리할 때 사용하는 `systemd`가 정상적으로 동작하는지 확인합니다.

이 미션에서는 SSH, cron 같은 서비스를 확인하고 제어해야 하므로 `systemd` 사용 가능 여부가 중요합니다.

## 9.1 PID 1 확인

### 실행 명령

```bash
ps -p 1 -o comm=
```

### 명령어 뜻

- `ps`: 실행 중인 프로세스를 확인합니다.
- `-p 1`: PID 1번 프로세스만 확인합니다.
- `-o comm=`: 프로그램 이름만 간단히 표시합니다.

### 정상 출력

```text
systemd
```

### 왜 PID 1을 보나요?

Linux에서 PID 1은 시스템 시작 후 가장 먼저 실행되는 핵심 프로세스입니다. 일반 Ubuntu VM에서는 보통 `systemd`입니다.

## 9.2 systemctl 확인

### 실행 명령

```bash
systemctl --version
```

### 정상 출력 예시

```text
systemd 255 (...)
```

버전 숫자는 시스템마다 다를 수 있습니다.

### `[GO]`

다음을 모두 만족합니다.

- PID 1이 `systemd`
- `systemctl --version`이 정상 출력됨

### `[STOP]`

다음과 같은 경우에는 서비스 설정으로 넘어가지 않습니다.

- PID 1이 `systemd`가 아님
- `systemctl` 명령을 찾을 수 없음
- `System has not been booted with systemd`와 비슷한 오류가 발생함

Docker 컨테이너에서 흔히 발생할 수 있습니다.

# 10. 작업 6 — sudo 권한 확인

## 무엇을 확인하나요?

현재 일반 사용자가 필요할 때 관리자 권한을 사용할 수 있는지 확인합니다.

SSH, UFW, 사용자·그룹 설정은 시스템 영역을 수정하므로 `sudo` 권한이 필요합니다.

### 실행 명령

```bash
sudo -v
```

### 명령어 뜻

`sudo -v`는 시스템 설정을 변경하지 않고 현재 사용자가 sudo 인증을 받을 수 있는지 확인합니다.

처음 실행하면 현재 사용자 비밀번호를 물어볼 수 있습니다.

### 정상 결과

성공하면 일반적으로 아무 메시지도 출력되지 않고 프롬프트로 돌아옵니다.

### 종료 코드 확인

바로 다음 명령을 실행합니다.

```bash
echo $?
```

정상이라면 다음처럼 출력됩니다.

```text
0
```

### 종료 코드란?

명령이 끝난 뒤 Linux는 성공 또는 실패 여부를 숫자로 남깁니다.

- `0`: 성공
- `0`이 아닌 값: 실패 또는 별도 상태

### `[GO]`

`sudo -v`가 성공하고 종료 코드가 `0`입니다.

### `[STOP]`

다음과 같은 메시지가 나오면 중단합니다.

```text
user is not in the sudoers file
```

또는 sudo 권한이 없다는 메시지가 나오면 관리자 권한이 있는 계정을 확보해야 합니다.

# 11. 작업 7 — 필수 명령과 도구 확인

## 무엇을 확인하나요?

미션에서 사용할 프로그램이 설치되어 있는지 확인합니다.

이 단계에서는 **설치 여부만 확인**합니다. 없는 도구가 있다고 바로 당황할 필요는 없습니다. 아래 12장에서 필요한 패키지만 설치합니다.

---

## 11.1 OpenSSH Server 확인

SSH는 다른 컴퓨터에서 서버 터미널에 접속하는 기능입니다.

```bash
command -v sshd || echo "[MISSING] openssh-server"
```

정상 예시:

```text
/usr/sbin/sshd
```

`[MISSING]`이 나오면 OpenSSH Server가 설치되지 않은 상태입니다.

---

## 11.2 UFW 확인

UFW는 **Uncomplicated Firewall**의 약자로 Ubuntu에서 방화벽 규칙을 쉽게 관리하는 도구입니다.

```bash
command -v ufw || echo "[MISSING] ufw"
```

정상 예시:

```text
/usr/sbin/ufw
```

---

## 11.3 cron 확인

cron은 정해진 시간마다 명령을 자동 실행하는 기능입니다. 나중에 `monitor.sh`를 매분 실행하는 데 사용합니다.

```bash
command -v crontab || echo "[MISSING] cron"
```

정상 예시:

```text
/usr/bin/crontab
```

---

## 11.4 ACL 도구 확인

ACL은 **Access Control List**의 약자로 기본 소유자·그룹 권한보다 더 세밀하게 접근 권한을 설정할 때 사용합니다.

```bash
command -v setfacl || echo "[MISSING] acl"
```

```bash
command -v getfacl || echo "[MISSING] acl"
```

정상이라면 `/usr/bin/setfacl`, `/usr/bin/getfacl` 같은 경로가 출력됩니다.

---

## 11.5 ss 확인

`ss`는 현재 어떤 TCP/UDP 포트가 열려 있는지 확인하는 도구입니다.

```bash
command -v ss || echo "[MISSING] iproute2"
```

정상 예시:

```text
/usr/bin/ss
```

---

## 11.6 logrotate 확인

logrotate는 로그 파일이 너무 커지지 않도록 회전·보관하는 도구입니다.

```bash
command -v logrotate || echo "[MISSING] logrotate"
```

정상 예시:

```text
/usr/sbin/logrotate
```

---

# 12. 작업 8 — 부족한 필수 패키지 설치

## 언제 실행하나요?

11장에서 `[MISSING]`이 하나라도 나온 경우에만 진행합니다.

모든 도구가 이미 있다면 이 절은 건너뛰어도 됩니다.

## 12.1 패키지 목록 갱신

### 실행 명령

```bash
sudo apt update
```

### 무엇을 하나요?

Ubuntu가 설치 가능한 프로그램 목록을 최신 상태로 갱신합니다. 프로그램 자체를 모두 업그레이드하는 명령은 아닙니다.

### 정상 결과

마지막 부분에 치명적인 오류 없이 패키지 목록 읽기가 완료되어야 합니다.

### `[STOP]`

다음과 같은 문제가 있으면 설치를 계속하지 않습니다.

- 네트워크 연결 실패
- 저장소 주소 오류
- `Could not get lock` 오류가 계속됨
- `sudo` 권한 오류

`Could not get lock`은 다른 `apt` 프로세스가 실행 중일 때 나타날 수 있습니다. 잠시 기다린 후 다시 확인하며, 잠금 파일을 임의로 삭제하지 않습니다.

## 12.2 필수 패키지 설치

```bash
sudo apt install -y openssh-server ufw cron acl iproute2 logrotate
```

### 패키지별 역할

| 패키지 | 역할 |
|---|---|
| `openssh-server` | SSH 서버 기능 |
| `ufw` | 방화벽 설정 |
| `cron` | 예약 실행 |
| `acl` | `setfacl`, `getfacl` 제공 |
| `iproute2` | `ss` 등 네트워크 확인 도구 제공 |
| `logrotate` | 로그 회전 및 보존 |

### `[CHECK]`

설치 후 11장의 확인 명령을 다시 실행해 `[MISSING]`이 사라졌는지 확인합니다.

# 13. 작업 9 — SSH 서비스 상태 확인

## 무엇을 확인하나요?

OpenSSH Server가 설치되어 있고 서비스 상태를 조회할 수 있는지 확인합니다.

아직 SSH 포트를 변경하지 않습니다. 포트 변경은 03장에서 안전 절차와 함께 진행합니다.

### 실행 명령

```bash
systemctl is-active ssh
```

### 가능한 결과

```text
active
```

또는

```text
inactive
```

### 의미

- `active`: SSH 서비스가 현재 실행 중
- `inactive`: 설치되어 있지만 현재 실행되지 않음

### `[CHECK]`

원격 SSH로 현재 서버에 접속 중이라면 보통 `active`여야 합니다.

로컬 콘솔에서 새 VM을 준비 중이고 `inactive`라면 이 장에서는 상태만 기록합니다. 실제 SSH 설정은 03장에서 진행합니다.

### 서비스 등록 상태 확인

```bash
systemctl is-enabled ssh
```

`enabled`라면 부팅 시 자동 시작하도록 등록된 상태입니다.

# 14. 작업 10 — cron 서비스 상태 확인

## 무엇을 확인하나요?

나중에 `monitor.sh`를 매분 자동 실행할 수 있도록 cron 서비스 사용 가능 여부를 확인합니다.

### 실행 명령

```bash
systemctl is-active cron
```

### 정상 출력

```text
active
```

### 등록 상태 확인

```bash
systemctl is-enabled cron
```

정상적인 Ubuntu 서버라면 보통 다음과 같습니다.

```text
enabled
```

### `[GO]`

cron이 `active`이고 서비스 관리가 정상적으로 가능합니다.

### `[STOP]`

`Unit cron.service could not be found`가 나온다면 `cron` 패키지가 설치되지 않은 상태일 수 있습니다. 12장의 설치 단계를 확인합니다.

# 15. 작업 11 — UFW 현재 상태 확인

## 무엇을 확인하나요?

현재 방화벽이 활성화되어 있는지 확인합니다.

이 단계에서는 **활성화하거나 규칙을 변경하지 않습니다.** 방화벽 설정은 04장에서 안전하게 진행합니다.

### 실행 명령

```bash
sudo ufw status verbose
```

### 가능한 출력 1

```text
Status: inactive
```

### 가능한 출력 2

```text
Status: active
```

### 중요한 점

현재 `inactive`여도 01장에서는 실패가 아닙니다. 미션 완료 시에는 방화벽을 활성화하고 TCP `20022`, `15034`만 필요한 범위에서 허용해야 합니다.

### `[CHECK]`

현재 상태를 기록합니다.

---

# 16. 작업 12 — 현재 IP 주소 확인

## 무엇을 확인하나요?

현재 Ubuntu 시스템이 사용하고 있는 IP 주소를 확인합니다.

SSH 접속 시험이나 다른 장치에서 서버로 접속할 때 필요할 수 있습니다.

### 실행 명령

```bash
hostname -I
```

### 정상 출력 예시

```text
192.168.0.50
```

가상환경에서는 여러 IP 주소가 동시에 표시될 수 있습니다.

### 주의

GitHub에 증빙을 올릴 때 개인 네트워크 구조를 불필요하게 공개할 필요는 없습니다. 평가에 필요하지 않은 IP 정보는 마스킹할 수 있습니다.

# 17. 작업 13 — 주요 포트가 이미 사용 중인지 확인

## 무엇을 확인하나요?

앞으로 사용할 두 포트가 이미 다른 프로그램에 사용되고 있는지 확인합니다.

- SSH 예정 포트: TCP `20022`
- Agent 포트: TCP `15034`

### 실행 명령

```bash
sudo ss -ltnp | grep -E ':(20022|15034)([[:space:]]|$)' || echo "[INFO] 20022/15034 LISTEN 없음"
```

### 쉬운 설명

- `ss -ltnp`: 현재 LISTEN 중인 TCP 포트와 프로세스를 확인합니다.
- `grep`: 그중 `20022`, `15034`만 찾습니다.
- 아무것도 없으면 `[INFO] 20022/15034 LISTEN 없음`을 표시합니다.

### 정상적인 초기 상태 예시

```text
[INFO] 20022/15034 LISTEN 없음
```

### `[STOP]`

두 포트 중 하나가 이미 다른 프로그램에 의해 사용 중이라면 해당 프로세스의 정체를 확인하기 전에는 SSH/Agent 설정을 진행하지 않습니다.

프로세스를 무조건 종료하거나 `kill -9`를 실행하지 않습니다.

---

# 18. 작업 14 — 디스크 여유 공간 확인

## 무엇을 확인하나요?

루트 파일시스템(`/`)의 전체 용량과 사용량을 확인합니다.

미션에서는 로그 파일이 계속 쌓이므로 디스크 공간이 완전히 부족하면 정상 수행이 어렵습니다.

### 실행 명령

```bash
df -h /
```

### 정상 출력 예시

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda2        50G   10G   38G  21% /
```

### 항목 뜻

- `Size`: 전체 용량
- `Used`: 사용 중인 용량
- `Avail`: 남은 용량
- `Use%`: 사용률
- `/`: 루트 파일시스템

### `[STOP]`

`Use%`가 100%에 가깝거나 쓰기 작업이 불가능할 정도로 공간이 부족하면 먼저 디스크 공간을 확보합니다.

원본 미션에는 사전 준비 단계의 최소 여유 용량 수치가 지정되어 있지 않으므로 임의의 합격 기준을 만들지는 않습니다.

# 19. 작업 15 — 메모리와 CPU 기본 상태 확인

## 왜 미리 보나요?

나중에 `monitor.sh`가 CPU와 메모리 사용률을 수집합니다. 지금 기본 상태를 한 번 확인해 두면 이후 결과를 이해하기 쉽습니다.

### 메모리 확인

```bash
free -h
```

### CPU와 시스템 부하 확인

```bash
uptime
```

이 단계의 값은 합격·불합격을 판단하기 위한 것이 아니라 **초기 상태를 파악하기 위한 참고값**입니다.

# 20. 작업 16 — 복구 수단 확인

## 왜 필요한가요?

다음 장 이후에는 SSH, 방화벽, 사용자 권한처럼 접속에 영향을 줄 수 있는 설정을 변경합니다.

잘못 설정하면 SSH 접속이 끊어질 수 있으므로 **설정을 바꾸기 전에 되돌아올 방법을 확보해야 합니다.**

## 환경별 최소 복구 수단

### VM을 사용하는 경우

- VM 콘솔에 직접 접속할 수 있는지 확인
- 가능하면 현재 상태 스냅샷 생성

### 클라우드 서버를 사용하는 경우

- 웹 콘솔 또는 Serial Console 사용 가능 여부 확인
- 복구 모드 접근 방법 확인

### 로컬 Ubuntu를 사용하는 경우

- 직접 키보드와 화면으로 로그인 가능한지 확인

### WSL2 / OrbStack을 사용하는 경우

- 호스트 Windows/macOS에서 Linux 인스턴스를 다시 열 수 있는지 확인
- 환경별 네트워크 차이를 참고 문서에서 확인

### `[STOP]`

SSH 연결 하나만 있고, 그 연결이 끊어졌을 때 서버에 다시 들어갈 다른 방법이 없다면 03장 SSH 설정 변경을 진행하지 않습니다.

자세한 내용은 [백업과 복구](./reference/backup-recovery.md)를 확인합니다.

# 22. 자주 발생하는 오류

## `sudo: command not found`

Ubuntu 최소 이미지에서 드물게 발생할 수 있습니다. 관리자 계정 또는 이미지 구성을 먼저 확인합니다. sudo 없이 시스템 변경을 강행하지 않습니다.

## `System has not been booted with systemd`

현재 환경이 Docker 컨테이너이거나 systemd를 사용하지 않는 환경일 수 있습니다. 본문 실습 환경과 맞는지 먼저 확인합니다.

## `Unit ssh.service could not be found`

OpenSSH Server가 설치되지 않았을 가능성이 큽니다.

```bash
sudo apt install -y openssh-server
```

설치 후 다시 상태를 확인합니다.

## `ufw: command not found`

```bash
sudo apt install -y ufw
```

## `setfacl: command not found`

```bash
sudo apt install -y acl
```

## `ss: command not found`

```bash
sudo apt install -y iproute2
```

## `Could not get lock /var/lib/dpkg/...`

다른 패키지 관리 프로세스가 실행 중일 수 있습니다. 잠시 기다린 뒤 다시 확인합니다. 입문 단계에서는 잠금 파일을 직접 삭제하지 않습니다.
