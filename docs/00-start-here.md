# 00. 시작 안내 — B1-1 전체 지도

> 이 장은 명령을 많이 실행하는 장이 아니라 **B1-1 전체를 머릿속에 넣고, 요구사항을 빠짐없이 수행하기 위한 지도**입니다.

## 1. B1-1을 한 문장으로 이해하기

> **Linux 서버의 접속·권한·Agent 환경을 안전하게 구성하고, Bash 모니터링을 자동화하여 상태를 기록·검증·복구할 수 있게 만든다.**

이번 미션은 단순한 Linux 명령어 암기가 아닙니다.

`보안 설정 → 권한 설계 → 애플리케이션 실행 → 상태 감시 → 자동 실행 → 로그 관리 → 장애 대응 → 증빙`

이라는 실제 서버 운영 흐름을 직접 구현합니다.

---

## 2. Source of Truth — 무엇을 가장 먼저 믿을 것인가

요구사항이 서로 다르게 보일 때는 다음 우선순위를 사용합니다.

1. `b1-1-mission.md` / 원본 PDF — 미션 요구사항
2. `b1-1-evaluation.md` — 평가 기준
3. `docs/reference/requirements-evidence-map.md` — 요구사항 추적표
4. `docs/00~15` — 실행·학습 안내서
5. `scripts/`, `config/`, `tests/` — 실제 구현
6. `reports/`, `evidence/` — 실제 결과와 증거

문서 편의를 위해 원본 요구사항을 임의로 바꾸지 않습니다.

---

## 3. 최종 결과물

원본 미션의 핵심 제출물은 두 가지입니다.

### 3.1 요구사항 수행 내역서

다음 내용을 실제 결과와 함께 기록합니다.

- SSH 포트 `20022` 및 Root 원격 로그인 차단
- 방화벽 활성화 및 `20022/tcp`, `15034/tcp` 허용
- 사용자·그룹·ACL
- 디렉터리·파일 권한
- Agent 환경변수와 실행 결과
- Boot Sequence 5단계 `[OK]`
- `Agent READY`
- `0.0.0.0:15034` LISTEN
- `monitor.sh` 실행 및 실패 처리
- CPU·MEM·DISK 수집과 임계값 경고
- `monitor.log` 누적
- cron 매분 자동 실행
- 로그 `10MB / 10개` 관리
- 오류·복구·재검증
- 필수 증빙

수행 결과는 `reports/`에 설명하고, 실제 근거는 `evidence/`에 보관합니다.

### 3.2 `monitor.sh`

최종 요구사항은 다음과 같습니다.

```text
경로   : $AGENT_HOME/bin/monitor.sh
소유자 : agent-dev
그룹   : agent-core
권한   : 750 (rwxr-x---)
실행자 : agent-admin (cron)
```

## 4. 환경 기준 — 미션 기준과 실제 실습을 구분한다

### 원본 미션 기준

```text
운영체제 : Ubuntu 22.04 또는 동등 Linux 환경
셸       : Bash
```

### 현재 실제 검증 환경

```text
운영체제      : Ubuntu 24.04.4 LTS (Noble Numbat)
CPU           : x86_64
PID 1         : systemd
systemd       : 255
OpenSSH       : 설치 확인
UFW           : 설치 확인
cron          : 설치 확인
ACL 도구      : getfacl / setfacl 설치 확인
ss            : 설치 확인
logrotate     : 설치 확인
```

Ubuntu 24.04.4는 **이번 실제 실습 환경**이며, 미션 자체를 Ubuntu 24.04 전용으로 바꾸지 않습니다.

WSL2·OrbStack·Docker처럼 서비스·네트워크 동작이 다른 환경은 [환경별 차이](./reference/environment-differences.md)에서 별도로 다룹니다.

## 5. 고정값

미션에서 반드시 고정되는 값과 안내서에서 선택하는 값을 구분합니다.

### 미션 고정값

```text
SSH_PORT=20022
AGENT_PORT=15034
AGENT_LOG_DIR=/var/log/agent-app
KEY_FILE=t_secret.key
```

### AGENT_HOME

원본 미션은 다음 경로를 **예시**로 제시합니다.

```text
/home/agent-admin/agent-app
```

이 안내서에서는 입문자가 경로와 소유권을 이해하기 쉽고 원본 예시와의 차이를 줄이기 위해 다음을 표준 경로로 사용합니다.

```bash
AGENT_HOME=/home/agent-admin/agent-app
AGENT_PORT=15034
AGENT_UPLOAD_DIR=$AGENT_HOME/upload_files
AGENT_KEY_PATH=$AGENT_HOME/api_keys/t_secret.key
AGENT_LOG_DIR=/var/log/agent-app
```

> 경로 자체보다 중요한 것은 모든 설정·스크립트·검증이 동일한 `AGENT_HOME`을 사용하는 것입니다.

## 6. 사용자와 그룹

### 사용자

| 사용자 | 역할 |
|---|---|
| `agent-admin` | 운영·관리, cron 실행 |
| `agent-dev` | 개발·운영, `monitor.sh` 소유 |
| `agent-test` | QA·권한 테스트 |

### 그룹

| 그룹 | 구성원 | 핵심 역할 |
|---|---|---|
| `agent-common` | admin, dev, test | 공용 `upload_files` 접근 |
| `agent-core` | admin, dev | `api_keys`, 로그 등 중요 자원 접근 |

핵심 원칙은 **Least Privilege, 최소 권한**입니다.

`agent-test`는 공용 자원은 사용할 수 있지만 키와 운영 로그 같은 핵심 자원에는 접근하지 못해야 합니다.

# 7. 학습 지도 — `00 + 5 × 3`

15개 단계를 각각 외우지 않습니다.

```text
00 전체 지도

① 준비와 접근
01 환경 → 02 저장소 → 03 SSH

② 시스템 구성
04 방화벽 → 05 권한 → 06 Agent

③ 구현과 자동화
07 Monitor → 08 자동화 → 09 테스트

④ 검증과 평가
10 장애 → 11 증빙 → 12 평가

⑤ 완성과 고도화
13 재현 → 14 제출 → 15 보너스
```

## 기억할 5개 단어

> **준비 → 구성 → 구현 → 검증 → 완성**

## 15단계 한 줄 기억법

```text
01 환경   : 바꾸기 전에 환경부터 확인한다.
02 저장소 : 작업은 추적 가능하게 기록한다.
03 SSH    : 서버의 접속 입구를 안전하게 만든다.

04 방화벽 : 필요한 문만 열고 나머지는 막는다.
05 권한   : 필요한 사람에게 필요한 권한만 준다.
06 Agent  : 일반 사용자 환경에서 앱을 실행한다.

07 Monitor: 서버와 Agent 상태를 자동으로 감시한다.
08 자동화 : 감시를 반복하고 로그를 보존한다.
09 테스트 : 정상과 장애를 실제로 시험한다.

10 장애   : 실패 원인을 찾고 복구한다.
11 증빙   : 했다는 사실을 객관적으로 증명한다.
12 평가   : 구현뿐 아니라 이유까지 설명한다.

13 재현   : 처음부터 다시 해도 성공해야 한다.
14 제출   : 누락과 비밀정보를 없애고 완성한다.
15 보너스 : 통과에서 멈추지 않고 한 단계 확장한다.
```

## 8. 각 문서의 공통 학습 형식

`01~15`는 가능한 한 같은 구조로 작성합니다.

```text
① 목표
② 이해
③ 실행
④ 확인
⑤ 오류·복구
⑥ 기억
```

각 장 마지막에는 최소한 다음을 남깁니다.

- 한 문장 요약
- 핵심어 3개
- 핵심 명령 또는 핵심 동작
- 스스로 설명할 질문
- 다음 단계

이를 통해 긴 문서를 통째로 외우지 않고 핵심 구조를 반복 학습합니다.

## 9. 실행 상태 표시

| 표시 | 의미 | 행동 |
|---|---|---|
| `[CHECK]` | 결과 확인 | 예상 결과와 실제 결과 비교 |
| `[GO]` | 진행 가능 | 다음 작업으로 이동 |
| `[STOP]` | 즉시 중단 | 원인을 해결하기 전 진행 금지 |
| `[RECOVERY]` | 복구 | 정상 상태로 되돌림 |
| `[EVIDENCE]` | 증빙 | 객관적 근거 저장 |
| `[WARN]` | 주의 | 위험·차이를 확인 |

리눅스 명령의 일반적인 종료 코드는 다음처럼 이해합니다.

```text
0     = 성공
0 외  = 실패 또는 별도 상태
```

직전 종료 코드는 `echo $?`로 확인할 수 있습니다.

## 10. PASS 규칙 — 구현만 하면 끝이 아니다

각 단계는 다음 세 조건이 모두 만족되어야 완료입니다.

```text
구현
 +
테스트
 +
증빙
 = PASS
```

예를 들어 `Port 20022`를 설정 파일에 적었다고 SSH 단계가 끝난 것이 아닙니다.

```text
설정 작성
→ sshd 문법검사
→ 실제 20022 LISTEN 확인
→ Root 로그인 정책 확인
→ 증빙 저장
→ PASS
```

전체 추적은 [요구사항-검증-증빙 대응표](./reference/requirements-evidence-map.md)를 기준으로 합니다.

## 11. 반드시 지킬 안전 규칙

### SSH

- 설정 변경 전에 백업합니다.
- 원격 작업이라면 복구 가능한 세션을 확보합니다.
- `sshd -t` 성공 전에는 서비스를 재시작하지 않습니다.
- 새 포트를 방화벽에서 확보한 뒤 기존 접속로를 변경합니다.
- 변경 후 실제 LISTEN과 새 접속을 확인합니다.

### 권한

- `chmod -R 777`로 문제를 덮지 않습니다.
- 사용자·그룹·ACL 목적을 먼저 정하고 권한을 부여합니다.
- 중요한 디렉터리에 `agent-test`가 접근할 수 없는지 실제로 시험합니다.

### Root

- Agent를 Root로 실행하지 않습니다.
- `sudo`는 시스템 설정이 필요한 경우에만 사용합니다.

### 비밀정보

Git에 다음을 넣지 않습니다.

- 실제 API key
- 비밀번호
- 토큰
- 실제 `.env`
- 민감한 시스템 백업

`t_secret.key`의 **존재·경로·권한은 증빙하되 실제 값은 노출하지 않습니다.**

## 12. 요구사항 누락을 막는 방법

문서 목차만 믿지 않고 모든 요구사항을 다음 구조로 추적합니다.

```text
원본 Mission
      ↓
Requirement ID
      ↓
구현 파일/설정
      ↓
검증 명령·테스트
      ↓
Evidence
      ↓
평가문항
      ↓
PASS / FAIL
```

마스터 표는 다음 파일입니다.

- [requirements-evidence-map.md](./reference/requirements-evidence-map.md)

이 표의 필수 요구사항이 모두 `PASS`가 되어야 B1-1 필수 미션을 완료한 것으로 판단합니다.

## 13. 보너스 과제도 수행 흐름에 포함한다

보너스는 삭제하지 않습니다.

원본 미션의 선택 과제인 다음 항목을 `15-bonus.md`에서 실제 구현·검증합니다.

- `report.sh`
- CPU/MEM/DISK 평균·최대·최소 및 샘플 수
- 선택 시간 구간 분석
- 7일 경과 로그 압축
- archive 이동
- 30일 경과 아카이브 삭제
- 예외 처리

흐름은 다음과 같습니다.

```text
필수 미션 PASS
      ↓
15 Bonus
      ↓
실무 고도화
      ↓
포트폴리오/전문 훈련
```

## 14. 현재 실제 실습에서 확인된 상태

현재까지 실제 Ubuntu 환경에서 다음을 확인했습니다.

```text
환경        : Ubuntu 24.04.4 LTS / x86_64 / systemd
sudo        : 정상
필수 도구   : SSH, UFW, cron, ACL, ss, logrotate 확인
SSH         : 20022 LISTEN 확인
Root SSH    : PermitRootLogin no 확인
UFW         : active
Incoming    : default deny
허용 포트   : 20022/tcp, 15034/tcp
사용자      : 아직 생성 전
그룹        : agent-common, agent-core 생성 단계 진행
Agent 이후  : 미진행
```

이 상태는 **대화에서 실제 확인한 진행 기록**이며, 최종 `PASS`는 별도의 evidence 파일과 재검증까지 완료한 뒤 부여합니다.

## 15. 이번 장 완료 확인

- [ ] B1-1을 한 문장으로 설명할 수 있다.
- [ ] 원본 미션과 평가문서가 최우선 기준임을 안다.
- [ ] 미션 기준 환경과 현재 실제 실습 환경을 구분한다.
- [ ] `준비 → 구성 → 구현 → 검증 → 완성` 5개 묶음을 기억한다.
- [ ] `01~15`가 5개 묶음 × 3단계라는 것을 이해한다.
- [ ] `PASS = 구현 + 테스트 + 증빙`임을 이해한다.
- [ ] Secret 값을 Git에 저장하지 않는다는 것을 이해한다.
- [ ] Bonus도 15단계에서 구현·검증한다는 것을 확인했다.

## 이번 단계 기억하기

**한 문장**  
B1-1은 서버를 안전하게 구성하고 스스로 상태를 감시·기록·검증하게 만드는 미션이다.

**핵심어 3개**  
`구성 · 감시 · 증빙`

**설명할 질문**  
“왜 설정만 완료해서는 미션을 통과했다고 볼 수 없는가?”

**정답 핵심**  
실제 동작 테스트와 객관적인 증빙까지 있어야 요구사항 충족을 증명할 수 있기 때문이다.
