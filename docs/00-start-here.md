# 00. 시작 안내 — 먼저 읽고 시작하세요

> 이 장에서는 시스템 설정을 변경하지 않습니다.  
> 문서의 사용법과 안전 규칙을 먼저 확인한 뒤, 다음 장부터 명령어를 하나씩 실행합니다.

## 1. 이번 장에서 하는 일

이 장에서는 다음 내용을 먼저 확정합니다.

- B1-1 미션에서 최종적으로 만들어야 하는 결과물
- 실습의 기준 운영체제와 실행 환경
- 계속 사용할 사용자, 그룹, 경로, 포트
- 문서에 표시되는 `[GO]`, `[STOP]`, `[CHECK]`의 의미
- 입문자가 실수하지 않기 위한 안전 규칙
- 다음 장으로 넘어가기 위한 완료 조건

### 왜 먼저 확인해야 하나요?

리눅스 실습에서는 **같은 명령어라도 어떤 사용자로 실행하는지, 어떤 경로에서 실행하는지, 어떤 운영체제를 쓰는지에 따라 결과가 달라질 수 있습니다.**

그래서 처음부터 명령어를 입력하기보다, 먼저 기준을 하나로 맞춰 두어야 실수를 줄일 수 있습니다.

쉽게 말하면, 이 장은 **“실습을 시작하기 전에 지도와 안전수칙을 읽는 단계”**입니다.

---

## 2. 미션을 쉬운 말로 이해하기

이 미션의 목표는 **리눅스 서버가 자신의 상태를 자동으로 점검하고, 결과를 로그로 남기게 만드는 것**입니다.

실습 과정에서 다음 작업을 수행합니다.

1. SSH 접속을 더 안전하게 설정합니다.
2. 방화벽에서 필요한 포트만 허용합니다.
3. 역할에 따라 사용자와 그룹을 나눕니다.
4. Agent 애플리케이션을 일반 사용자로 실행합니다.
5. `monitor.sh`로 프로세스, 포트, CPU, 메모리, 디스크를 점검합니다.
6. cron으로 `monitor.sh`를 매분 자동 실행합니다.
7. 정상 상태와 장애 상태를 직접 검증하고 증빙을 남깁니다.

### 각각 무엇을 의미하나요?

- **SSH 보안 설정**: 다른 컴퓨터에서 서버에 접속하는 입구를 더 안전하게 만드는 작업입니다.
- **방화벽 설정**: 서버의 여러 통신 입구 중 실제로 필요한 것만 열어 두는 작업입니다.
- **사용자·그룹 분리**: 운영자, 개발자, 테스트 사용자의 권한을 역할에 맞게 나누는 작업입니다.
- **Agent 실행**: 제공된 애플리케이션이 지정된 환경에서 정상적으로 실행되는지 확인하는 작업입니다.
- **`monitor.sh` 구현**: 서버와 Agent의 상태를 자동으로 확인하는 Bash 스크립트를 만드는 핵심 작업입니다.
- **cron 자동 실행**: 사람이 직접 실행하지 않아도 정해진 주기마다 `monitor.sh`가 실행되도록 만드는 작업입니다.
- **증빙 기록**: “설정했다”라고 말하는 데서 끝나지 않고 실제 명령 출력으로 정상 동작을 증명하는 작업입니다.

## 3. 최종 제출물

원본 미션에서 요구하는 핵심 제출물은 다음 2가지입니다.

### 3.1 요구사항 수행 내역서

다음 내용을 하나의 수행 내역서로 정리합니다.

- SSH 설정
- 방화벽 규칙
- 사용자·그룹·ACL 설정
- 디렉터리와 권한
- 환경변수
- Agent 실행 결과
- `monitor.sh` 실행 결과
- 로그 누적 결과
- cron 자동 실행 결과
- 오류와 복구 과정
- 필수 증빙 자료

### 쉽게 말하면

수행 내역서는 **“내가 무엇을 어떻게 설정했고, 실제로 잘 동작했다는 것을 보여 주는 작업 기록”**입니다.

예를 들어 SSH 포트를 `20022`로 변경했다면 단순히 “변경 완료”라고 쓰는 것이 아니라, 실제 설정 파일과 포트 LISTEN 결과를 함께 기록합니다.

이 저장소에서는 실제 수행 기록을 `reports/`와 `evidence/`에 나누어 관리한 뒤, 제출 시 하나의 수행 내역서로 정리합니다.

- `reports/`: 작업 과정과 결과를 사람이 읽기 쉽게 정리합니다.
- `evidence/`: 명령 출력, 로그, 화면 캡처처럼 실제 근거를 보관합니다.

### 3.2 `monitor.sh`

시스템 상태를 수집하고 로그로 기록하는 Bash 스크립트입니다.

최종 위치와 권한은 다음과 같습니다.

```text
경로   : $AGENT_HOME/bin/monitor.sh
소유자 : agent-dev
그룹   : agent-core
권한   : 750 (rwxr-x---)
```

### 쉽게 말하면

`monitor.sh`는 이번 미션에서 직접 만드는 **자동 점검 프로그램**입니다.

이 파일이 실행되면 다음과 같은 질문에 자동으로 답할 수 있어야 합니다.

- Agent가 실행 중인가?
- Agent 포트가 열려 있는가?
- CPU 사용량은 높은가?
- 메모리는 얼마나 사용 중인가?
- 디스크 공간은 충분한가?
- 확인 결과를 로그에 남겼는가?

## 4. 이 안내서의 기준 환경

본문은 다음 환경을 기준으로 작성합니다.

```text
운영체제       : Ubuntu 24.04 LTS
CPU 아키텍처   : x86_64
서비스 관리자  : systemd
SSH            : OpenSSH Server
방화벽         : UFW
자동 실행      : cron
명령어 셸      : Bash
```

### 각 항목 설명

- **Ubuntu 24.04 LTS**: 실습의 기준이 되는 리눅스 운영체제입니다. LTS(Long Term Support)는 장기간 지원되는 버전이라는 뜻입니다.
- **x86_64**: 일반적인 Intel/AMD 64비트 CPU 환경을 의미합니다. Agent 실행 파일 선택 시 중요합니다.
- **systemd**: SSH나 cron 같은 서비스를 시작·중지·확인하는 서비스 관리자입니다.
- **OpenSSH Server**: 원격에서 안전하게 서버 터미널에 접속할 수 있게 해 주는 프로그램입니다.
- **UFW (Uncomplicated Firewall)**: Ubuntu에서 비교적 쉽게 방화벽 규칙을 설정할 수 있게 해 주는 도구입니다.
- **cron**: 정해진 시간마다 명령이나 스크립트를 자동 실행하는 기능입니다.
- **Bash (Bourne Again Shell)**: 이번 미션의 자동화 스크립트를 작성할 셸 언어입니다.

### 다른 환경을 사용할 때

WSL2, OrbStack, Docker 또는 실제 원격 서버에서는 일부 동작이 다를 수 있습니다.

- 본문의 명령어를 임의로 바꾸지 않습니다.
- 먼저 [환경별 차이](./reference/environment-differences.md)를 확인합니다.
- 환경 차이가 불명확하면 해당 단계에서 멈춥니다.
- 최종 재현 시험은 깨끗한 Ubuntu 24.04 환경에서 수행하는 것을 기준으로 합니다.

### 왜 한 환경으로 고정하나요?

입문자가 여러 환경용 명령을 동시에 보면 어떤 명령을 선택해야 하는지 혼란스러울 수 있습니다.

그래서 본문은 **한 가지 기준 환경으로 통일**하고, WSL2나 OrbStack 같은 차이는 참고 문서에서 별도로 설명합니다.

## 5. 계속 사용할 고정값

아래 값은 이후 모든 문서와 스크립트에서 동일하게 사용합니다.

| 구분 | 고정값 | 의미 |
|---|---|---|
| Agent 기본 경로 | `/opt/agent-app` | Agent 파일과 하위 디렉터리의 기준 위치 |
| Agent 포트 | `15034` | Agent 애플리케이션이 사용하는 TCP 포트 |
| 업로드 경로 | `/opt/agent-app/upload_files` | 공용 업로드 파일 저장 위치 |
| 키 파일 경로 | `/opt/agent-app/api_keys/t_secret.key` | Agent가 읽는 키 파일 위치 |
| 로그 경로 | `/var/log/agent-app` | 모니터링 로그 저장 위치 |
| SSH 포트 | `20022` | 변경 후 사용할 SSH TCP 포트 |

환경변수로 표현하면 다음과 같습니다.

```bash
AGENT_HOME=/opt/agent-app
AGENT_PORT=15034
AGENT_UPLOAD_DIR=/opt/agent-app/upload_files
AGENT_KEY_PATH=/opt/agent-app/api_keys/t_secret.key
AGENT_LOG_DIR=/var/log/agent-app
```

### 각 변수 설명

- **`AGENT_HOME`**: Agent 관련 파일이 모이는 가장 위쪽 기준 디렉터리입니다.
- **`AGENT_PORT`**: Agent가 네트워크 요청을 받을 포트 번호입니다.
- **`AGENT_UPLOAD_DIR`**: Agent가 사용하는 업로드 파일을 저장하는 위치입니다.
- **`AGENT_KEY_PATH`**: Agent가 읽는 키 파일의 정확한 경로입니다.
- **`AGENT_LOG_DIR`**: Agent와 모니터링 관련 로그를 저장할 디렉터리입니다.

### 왜 환경변수를 사용하나요?

스크립트 안에 경로와 포트를 여러 번 직접 적으면 나중에 값을 바꿀 때 실수하기 쉽습니다.

환경변수를 사용하면 **한 곳에서 값을 정하고 여러 프로그램이 같은 값을 공유**할 수 있습니다.

> 원본 미션의 `AGENT_HOME` 경로는 예시입니다. 이 안내서에서는 모든 문서와 검증 기준을 일치시키기 위해 `/opt/agent-app`으로 고정합니다.

## 6. 사용자와 그룹

### 6.1 사용자

| 사용자 | 역할 |
|---|---|
| `agent-admin` | 운영·관리 및 cron 실행 |
| `agent-dev` | 개발·운영 및 `monitor.sh` 작성 |
| `agent-test` | QA·테스트 |

### 왜 사용자를 나누나요?

모든 사람이 같은 계정을 사용하면 누가 어떤 작업을 해야 하는지 구분하기 어렵고, 필요 이상으로 많은 권한을 줄 수 있습니다.

역할별 계정을 나누면 **필요한 사람에게 필요한 권한만 주는 최소 권한 원칙**을 적용할 수 있습니다.

- `agent-admin`: 운영과 자동 실행을 담당합니다.
- `agent-dev`: 스크립트 작성과 개발 관련 작업을 담당합니다.
- `agent-test`: 권한이 제한된 상태에서 테스트를 수행합니다.

### 6.2 그룹

| 그룹 | 포함 사용자 | 역할 |
|---|---|---|
| `agent-common` | `agent-admin`, `agent-dev`, `agent-test` | 공용 업로드 디렉터리 사용 |
| `agent-core` | `agent-admin`, `agent-dev` | 키와 로그 등 중요 자원 사용 |

### 왜 그룹을 사용하나요?

사용자마다 권한을 하나씩 설정하면 관리가 복잡해집니다.

그룹을 사용하면 **같은 역할의 사용자를 묶어서 한 번에 권한을 관리**할 수 있습니다.

예를 들어 `agent-test`는 공용 업로드 디렉터리는 사용할 수 있지만, 중요한 키 파일에는 접근하지 못하도록 구성할 수 있습니다.

사용자와 그룹은 아직 생성하지 않습니다. 실제 생성은 [05. 사용자·그룹·ACL](./05-users-groups-acl.md)에서 진행합니다.

## 7. 실행 계정 표시법

각 명령어 위에는 **누가 실행해야 하는지** 표시합니다.

| 표시 | 의미 |
|---|---|
| `[현재 sudo 사용자]` | Ubuntu를 처음 준비할 때 사용하는 기존 관리자 계정 |
| `[agent-admin]` | 운영과 cron 실행용 계정 |
| `[agent-dev]` | 스크립트 작성과 실행용 계정 |
| `[agent-test]` | 접근 권한 시험용 계정 |

### 왜 실행 계정을 확인해야 하나요?

리눅스에서는 같은 명령어라도 실행하는 사용자에 따라 결과가 달라집니다.

예를 들어 어떤 파일은 `agent-dev`는 읽을 수 있지만 `agent-test`는 읽지 못하도록 설정할 수 있습니다.

따라서 명령어를 복사하기 전에 반드시 **현재 로그인한 사용자와 문서에 표시된 실행 계정이 같은지 확인**해야 합니다.

실행 계정이 다르면 같은 명령어도 결과가 달라질 수 있으므로 반드시 표시를 확인합니다.

## 8. 문서 상태 표시법

| 표시 | 의미 | 행동 |
|---|---|---|
| `[CHECK]` | 결과를 확인해야 함 | 예상 결과와 실제 결과를 비교합니다. |
| `[GO]` | 다음 단계로 진행 가능 | 완료 체크 후 다음 작업으로 이동합니다. |
| `[STOP]` | 즉시 중단해야 함 | 다음 명령을 실행하지 않습니다. |
| `[RECOVERY]` | 복구 절차 | 정상 상태로 되돌린 뒤 다시 검증합니다. |
| `[EVIDENCE]` | 증빙 저장 | 명령 출력이나 화면을 지정 위치에 저장합니다. |
| `[WARN]` | 주의가 필요함 | 내용을 읽고 위험 여부를 판단합니다. |

### 쉽게 기억하는 방법

```text
CHECK    = 결과 확인
GO       = 계속 진행
STOP     = 즉시 중단
RECOVERY = 복구
EVIDENCE = 증거 저장
WARN     = 주의
```

### 왜 이런 표시를 사용하나요?

입문자는 명령어 실행 자체보다 **“이 결과가 정상인지 아닌지”를 판단하는 것이 더 어렵습니다.**

그래서 각 단계마다 다음 행동을 명확하게 표시해 두어 잘못된 상태에서 계속 진행하는 것을 방지합니다.

## 9. 명령어 실행 방법

명령어는 다음 원칙으로 실행합니다.

1. 한 번에 **한 개의 코드 블록만** 실행합니다.
2. `$`, `#` 같은 터미널 프롬프트 문자는 입력하지 않습니다.
3. 명령어를 실행하기 전에 실행 계정과 현재 위치를 확인합니다.
4. 명령 실행 후 예상 출력과 종료 코드를 확인합니다.
5. `[GO]` 조건을 만족하기 전에는 다음 단계로 넘어가지 않습니다.
6. `[STOP]`이 나오면 같은 명령을 반복하지 않습니다.
7. 오류 메시지를 생략하지 말고 처음부터 끝까지 기록합니다.

### 예시

문서에 다음과 같이 보인다고 가정합니다.

```bash
whoami
```

터미널에는 `whoami`만 입력합니다.

```text
$ whoami   ← `$`는 입력하지 않음
```

### 종료 코드란 무엇인가요?

리눅스 명령은 실행이 끝나면 숫자로 성공 여부를 남깁니다.

- `0`: 일반적으로 정상 종료
- `0이 아닌 값`: 오류 또는 특별한 상태

직전 명령의 종료 코드는 다음 명령으로 확인할 수 있습니다.

```bash
echo $?
```

이후 실습에서는 **출력 내용과 종료 코드를 함께 확인**합니다.

## 10. 반드시 지킬 안전 규칙

### 10.1 SSH 설정을 바꾸기 전

- 기존 SSH 세션을 닫지 않습니다.
- 로컬 콘솔 또는 복구 가능한 접속 방법을 먼저 확보합니다.
- SSH 설정 파일을 백업합니다.
- 방화벽에서 새 SSH 포트 `20022/tcp`를 먼저 허용합니다.
- `sshd -t`가 성공하기 전에는 SSH 서비스를 재시작하지 않습니다.

### 왜 중요한가요?

SSH 설정을 잘못 변경하면 **원격 서버에 다시 접속하지 못할 수 있습니다.**

그래서 항상 기존 연결을 유지한 상태에서 새 설정을 검증하고, 새 터미널에서 접속이 성공한 뒤 기존 세션을 종료합니다.

### 10.2 사용자와 권한을 바꾸기 전

- 현재 사용자와 sudo 권한을 확인합니다.
- 기존 경로의 소유권과 권한을 기록합니다.
- `chmod -R 777`과 같은 과도한 권한 부여는 사용하지 않습니다.
- 삭제 명령은 경로를 두 번 확인한 뒤 실행합니다.

### 왜 `777`을 피하나요?

`777`은 거의 모든 사용자에게 읽기·쓰기·실행 권한을 주는 매우 넓은 권한입니다.

문제가 생겼다고 무조건 `777`을 적용하면 일시적으로 동작할 수 있지만, 보안과 권한 설계를 망가뜨릴 수 있습니다.

### 10.3 비밀정보 관리

다음 정보는 Git에 커밋하지 않습니다.

- 실제 키 파일
- 비밀번호
- 토큰
- `.env` 파일
- 개인 IP 주소가 포함된 불필요한 출력
- 시스템 백업 원본

### 왜 중요한가요?

Git에 한 번 올라간 비밀정보는 나중에 파일을 삭제해도 **커밋 기록에 남을 수 있습니다.**

따라서 처음부터 비밀값을 Git 추적 대상에 넣지 않는 것이 가장 안전합니다.

키 파일의 **경로와 권한**은 증빙할 수 있지만, 키의 실제 내용은 화면과 문서에서 가립니다.

### 10.4 Root 사용 제한

- Agent 애플리케이션은 Root로 실행하지 않습니다.
- `monitor.sh`도 지정된 일반 사용자와 그룹 권한으로 운영합니다.
- `sudo`는 패키지 설치와 시스템 설정처럼 관리자 권한이 필요한 작업에만 사용합니다.

### 왜 Root로 실행하지 않나요?

Root는 시스템 전체를 변경할 수 있는 최고 권한입니다.

일반 프로그램을 Root로 실행하면 프로그램 오류나 보안 문제가 발생했을 때 시스템 전체에 영향을 줄 수 있습니다.

그래서 실제 서버 운영에서도 **필요한 권한만 가진 일반 사용자로 프로그램을 실행하는 방식**이 중요합니다.

## 11. 처음 보는 용어

| 용어 | 영문 | 쉬운 뜻 |
|---|---|---|
| Root | Root user | 리눅스의 최고 관리자 계정 |
| sudo | Superuser do | 일반 사용자가 관리자 권한으로 명령을 실행하는 도구 |
| SSH | Secure Shell | 다른 컴퓨터의 터미널에 안전하게 접속하는 방식 |
| Port | Port | 서비스가 통신할 때 사용하는 번호 |
| Firewall | Firewall | 허용한 네트워크 통신만 통과시키는 보안 장치 |
| Process | Process | 현재 실행 중인 프로그램 |
| Service | Service | 백그라운드에서 계속 실행되는 프로그램 |
| Log | Log | 시스템과 프로그램의 실행 기록 |
| cron | Cron | 정해진 시간마다 명령을 실행하는 기능 |
| ACL | Access Control List | 사용자별로 세밀하게 권한을 정하는 기능 |
| Environment Variable | 환경 변수 | 여러 프로그램이 공통으로 사용할 설정값 |
| PID | Process ID | 실행 중인 프로세스를 구분하는 번호 |
| TCP | Transmission Control Protocol | 네트워크에서 데이터를 안정적으로 전달하는 통신 방식 |
| LISTEN | Listening state | 프로그램이 특정 포트에서 접속을 기다리는 상태 |

### 용어를 전부 외워야 하나요?

아닙니다.

처음에는 **“어떤 역할을 하는지”만 이해하면 충분합니다.** 실제 명령을 사용하면서 반복해서 보면 자연스럽게 익숙해집니다.

## 12. 실습 진행 흐름

```text
00 시작 안내
→ 01 환경 준비
→ 02 저장소 작업 체계
→ 03 SSH 보안
→ 04 방화벽
→ 05 사용자·그룹·ACL
→ 06 Agent 실행
→ 07 monitor.sh 구현
→ 08 로그·cron
→ 09 정상·장애·복구 테스트
→ 10 트러블슈팅
→ 11 수행 내역·증빙
→ 12 평가 대비
→ 13 재현 시험
→ 14 최종 제출
→ 15 보너스
```

### 각 단계의 목적

| 단계 | 무엇을 하는가 | 완료되면 무엇이 남는가 |
|---|---|---|
| 00 | 실습 규칙 이해 | 기준과 안전수칙 확정 |
| 01 | Ubuntu 환경 점검 | 실습 가능한 환경 확인 |
| 02 | Git·증빙 체계 준비 | 작업 기록 구조 확정 |
| 03 | SSH 설정 | 안전한 원격 접속 구성 |
| 04 | 방화벽 설정 | 필요한 포트만 허용 |
| 05 | 사용자·그룹·ACL | 역할별 권한 구성 |
| 06 | Agent 실행 | `Agent READY`, `15034` 확인 |
| 07 | `monitor.sh` 구현 | 핵심 자동 점검 스크립트 완성 |
| 08 | cron·로그 관리 | 자동 실행과 로그 보존 |
| 09 | 정상·장애 시험 | 실패 감지와 복구 검증 |
| 10 | 오류 분석 | 트러블슈팅 기록 |
| 11 | 수행 내역·증빙 | 제출 근거 정리 |
| 12 | 평가 대비 | 왜 그렇게 구성했는지 설명 가능 |
| 13 | 재현 시험 | 처음부터 다시 수행 가능 확인 |
| 14 | 최종 검수 | 제출 준비 완료 |
| 15 | 보너스 | 필수 미션 이후 추가 학습 |

필수 미션은 14장까지입니다. 15장은 필수 항목을 모두 통과한 후 진행합니다.
