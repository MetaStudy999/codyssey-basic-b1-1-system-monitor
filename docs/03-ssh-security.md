# 03. SSH 보안 설정

> **기억 문장:** SSH는 백업하고, 검사하고, 새 포트가 열린 것을 확인한 뒤 전환한다.

이 장에서는 원본 B1-1 요구사항인 **SSH 포트 `20022` 사용**과 **Root 원격 로그인 차단**을 구현합니다.

---

## 1. 목표

최종 상태는 다음과 같습니다.

```text
SSH Port            = 20022
PermitRootLogin     = no
실제 LISTEN         = 20022
기존 22 LISTEN      = 없음
```

단순히 설정 파일에 값을 적는 것으로 끝내지 않고 다음 세 가지를 모두 확인합니다.

```text
설정값
+ 문법
+ 실제 LISTEN
```

---

## 2. 이해 — SSH에는 세 층이 있다

이번 Ubuntu 24.04.4 실습에서는 SSH를 이해할 때 다음 세 층을 구분해야 했습니다.

```text
① sshd 설정
   /etc/ssh/sshd_config
   /etc/ssh/sshd_config.d/*.conf

② ssh.service
   실제 sshd 프로세스를 실행

③ ssh.socket
   systemd가 SSH 포트를 먼저 LISTEN할 수 있음
```

현재 환경에서는 초기 상태가 다음과 같았습니다.

```text
ssh.socket  : active (listening)
ssh.service : inactive
Listen      : 0.0.0.0:22, [::]:22
```

즉 일반적인 `sshd.service` 상시 실행 방식만 생각하면 실제 포트 전환을 잘못 판단할 수 있습니다.

### Ubuntu 24.04에서 확인한 추가 동작

`Port 20022` 설정 후 `systemctl daemon-reload`를 수행하자 다음 자동 생성 설정이 확인되었습니다.

```text
/run/systemd/generator/ssh.socket.d/addresses.conf
```

내용의 핵심:

```ini
# Automatically generated by sshd-socket-generator

[Socket]
ListenStream=
ListenStream=0.0.0.0:20022
ListenStream=[::]:20022
```

즉 현재 Ubuntu 24.04.4 환경에서는 `sshd-socket-generator`가 SSH 설정의 포트를 읽어 `ssh.socket`의 주소를 자동 생성했습니다.

> 이 동작은 **현재 실습 환경에서 관찰한 구현 차이**입니다. 원본 미션이 Ubuntu 24.04 또는 socket activation을 요구한다는 뜻은 아닙니다.

---

## 3. 안전 순서

SSH 변경은 잘못하면 원격 접속을 잃을 수 있으므로 다음 순서를 사용합니다.

```text
현재 접속 방식 확인
→ 복구 수단 확인
→ 원본 백업
→ 현재 SSH 실행 방식 확인
→ 새 Port/Root 정책 작성
→ sshd 문법 검사
→ systemd 설정 재로딩
→ 실제 포트 전환
→ 20022 LISTEN 확인
→ 새 SSH 접속 확인
→ 기존 22 제거 확인
```

### 방화벽이 이미 active인 경우

SSH 포트를 바꾸기 전에 반드시 `20022/tcp`를 먼저 허용해야 합니다.

```bash
sudo ufw allow 20022/tcp
```

현재 실제 실습에서는 SSH 변경 당시 UFW가 `inactive`였고, 04장에서 `20022/tcp`와 `15034/tcp`를 허용한 뒤 UFW를 활성화했습니다.

---

## 4. 실행 전 확인

### 4.1 현재 SSH 포트

```bash
sudo ss -lntp | grep -E ':(22|20022)\b' || true
```

초기 실제 결과의 핵심:

```text
0.0.0.0:22
[::]:22
```

### 4.2 socket activation 확인

```bash
systemctl status ssh.socket --no-pager
```

실제 확인:

```text
Active: active (listening)
Triggers: ssh.service
Listen: 0.0.0.0:22
        [::]:22
```

원본 socket 정의 확인:

```bash
systemctl cat ssh.socket
```

초기 원본 핵심:

```ini
[Socket]
ListenStream=0.0.0.0:22
ListenStream=[::]:22
```

### 4.3 현재 터미널이 SSH인지 확인

```bash
printf 'SSH_CONNECTION=%s\nSSH_CLIENT=%s\n' "$SSH_CONNECTION" "$SSH_CLIENT"
```

현재 실제 실습에서는 두 값이 비어 있어 **로컬 콘솔/로컬 쉘**임을 확인한 뒤 변경했습니다.

원격 SSH 세션이라면 기존 세션을 닫지 말고 별도의 복구 수단을 확보합니다.

---

## 5. 원본 설정 백업

```bash
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.b1-1.backup
```

백업이 원본과 같은지 확인합니다.

```bash
sudo cmp -s /etc/ssh/sshd_config /etc/ssh/sshd_config.b1-1.backup \
  && echo "[OK] backup identical" \
  || echo "[ERROR] backup differs"
```

실제 결과:

```text
[OK] backup identical
```

`[ERROR]`가 나오면 다음 단계로 진행하지 않습니다.

---

## 6. B1-1 전용 SSH 설정

원본 `/etc/ssh/sshd_config`를 크게 수정하지 않고 별도 drop-in 파일을 사용합니다.

```bash
sudo tee /etc/ssh/sshd_config.d/99-b1-1.conf > /dev/null <<'EOF'
Port 20022
PermitRootLogin no
EOF
```

확인:

```bash
sudo cat /etc/ssh/sshd_config.d/99-b1-1.conf
```

목표 출력:

```text
Port 20022
PermitRootLogin no
```

### 왜 `PermitRootLogin no`인가

`without-password` 또는 `prohibit-password`는 Root의 비밀번호 인증을 제한하지만 다른 인증 방식까지 모두 차단한다는 의미는 아닙니다.

원본 미션의 **Root 원격 로그인 차단**을 명확히 만족시키기 위해 다음을 사용합니다.

```text
PermitRootLogin no
```

---

## 7. 문법 검사

설정을 서비스에 반영하기 전에 반드시 검사합니다.

```bash
sudo sshd -t && echo "[OK] sshd configuration syntax"
```

실제 결과:

```text
[OK] sshd configuration syntax
```

### `[STOP]`

`sshd -t`에서 오류가 나오면 SSH 서비스나 socket을 재시작하지 않습니다. 오류 메시지의 파일·라인을 먼저 수정합니다.

---

## 8. `Missing privilege separation directory: /run/sshd` 오류

실제 사전 검사 중 다음 오류가 발생했습니다.

```text
Missing privilege separation directory: /run/sshd
```

당시 상태를 확인하니:

```text
ssh.service : inactive (dead)
ssh.socket  : active
```

그리고 `ssh.service` 정의에는 다음이 있었습니다.

```ini
RuntimeDirectory=sshd
RuntimeDirectoryMode=0755
```

즉 `/run/sshd`는 사용자가 임의로 만드는 영구 디렉터리가 아니라 **systemd가 `ssh.service`를 시작할 때 생성하는 런타임 디렉터리**였습니다.

따라서 수동으로 `/run/sshd`를 만들지 않고 다음처럼 systemd를 통해 서비스를 시작해 확인했습니다.

```bash
sudo systemctl start ssh.service
```

이후 서비스 상태에서:

```text
ExecStartPre=/usr/sbin/sshd -t (status=0/SUCCESS)
Active: active (running)
```

을 확인했습니다.

### 학습 포인트

> 오류 메시지를 보고 바로 `mkdir /run/sshd`를 실행하지 말고, **누가 그 디렉터리를 관리해야 하는지 서비스 정의부터 확인**한다.

---

## 9. SSH 최종 해석값 확인

`/run/sshd`가 준비된 상태에서:

```bash
sudo sshd -T | grep -E '^(port|permitrootlogin) '
```

실제 확인 결과:

```text
port 20022
permitrootlogin no
```

이 결과는 `sshd`가 설정 파일을 최종적으로 해석한 값입니다.

---

## 10. Ubuntu 24.04 socket 설정 반영

SSH 설정 변경 후 systemd 설정을 다시 읽습니다.

```bash
sudo systemctl daemon-reload
```

이 환경에서는 다음 명령으로 자동 생성된 포트 설정을 확인할 수 있었습니다.

```bash
systemctl cat ssh.socket
```

핵심 결과:

```ini
# Automatically generated by sshd-socket-generator

[Socket]
ListenStream=
ListenStream=0.0.0.0:20022
ListenStream=[::]:20022
```

### 중복 override를 만들지 않는다

실습 중 `/etc/systemd/system/ssh.socket.d/override.conf`를 한 번 작성했지만, `sshd-socket-generator`가 이미 같은 설정을 자동 생성하는 것을 확인한 후 **중복 설정을 제거**했습니다.

최종 원칙:

```text
sshd Port 20022
    ↓
sshd-socket-generator
    ↓
ssh.socket 20022
```

원본 `/usr/lib/systemd/system/ssh.socket`을 직접 수정하지 않습니다.

---

## 11. 실제 포트 전환

당시 수동으로 시작해 22번을 사용하고 있던 `ssh.service`를 먼저 중지했습니다.

```bash
sudo systemctl stop ssh.service
```

확인:

```bash
systemctl is-active ssh.service ssh.socket
```

실제 결과:

```text
inactive
active
```

그 다음 socket을 새 설정으로 재시작했습니다.

```bash
sudo systemctl restart ssh.socket
```

---

## 12. 실제 LISTEN 검증

```bash
sudo ss -lntp | grep -E ':(22|20022)\b' || true
```

실제 최종 결과의 핵심:

```text
0.0.0.0:20022
[::]:20022
```

기존 `22`는 출력되지 않았습니다.

따라서 로컬 기준으로 다음이 검증되었습니다.

```text
20022 LISTEN = YES
22 LISTEN    = NO
```

---

## 13. 새 SSH 세션 검증

실제 서버를 원격으로 사용할 수 있는 환경에서는 별도 터미널에서 다음 형태로 접속 시험을 합니다.

```bash
ssh -p 20022 <일반사용자>@<서버주소>
```

### 성공 조건

- 일반 사용자로 `20022` 접속 성공
- 새 세션에서 `whoami` 정상
- 기존 세션을 닫기 전 새 세션 검증 완료

### 현재 상태

이번 작업은 **로컬 콘솔에서 수행**했기 때문에 실제 외부 클라이언트에서의 새 SSH 접속 증빙은 아직 별도 확보하지 않았습니다.

따라서 로컬 설정·LISTEN은 `TESTED`, 최종 외부 접속 증빙은 11장/13장에서 보완합니다.

---

## 14. Root 원격 로그인 검증

설정 해석값 확인:

```bash
sudo sshd -T | grep '^permitrootlogin '
```

목표:

```text
permitrootlogin no
```

가능한 재현 환경에서는 실제 Root SSH 접속 시도가 거부되는지도 확인할 수 있습니다. 단, 불필요하게 Root 비밀번호를 설정하거나 보안 정책을 약화시키면서 시험하지 않습니다.

---

## 15. 방화벽과의 연결

SSH 포트가 `20022`에서 LISTEN한다고 해서 네트워크 전체 구성이 끝난 것은 아닙니다.

다음 04장에서 확인할 내용:

```text
UFW active
20022/tcp ALLOW
15034/tcp ALLOW
기본 incoming deny
불필요한 22/tcp ALLOW 없음
```

즉:

```text
03 SSH = 프로그램이 20022에서 기다리게 함
04 UFW = 20022와 15034만 통과시키게 함
```

으로 구분합니다.

## 16. 오류와 복구

### `sshd -t` 실패

서비스를 재시작하지 않습니다. `99-b1-1.conf`의 오타와 기존 설정 충돌을 먼저 확인합니다.

### 20022가 LISTEN하지 않음

다음을 순서대로 확인합니다.

```bash
sudo sshd -t
systemctl status ssh.socket --no-pager
systemctl cat ssh.socket
sudo ss -lntp | grep -E ':(22|20022)\b' || true
```

### 원격 접속을 잃을 위험이 있음

기존 원격 세션을 닫지 않습니다. 로컬 콘솔/VM 콘솔 등 복구 경로를 먼저 확보합니다.

### 원래 22번으로 복구해야 함

UFW가 이미 활성화되어 있다면 **먼저 22/tcp 임시 허용 여부를 검토**한 뒤 SSH 설정을 되돌려야 합니다. 방화벽이 22를 막는 상태에서 SSH만 22로 되돌리면 원격 접속이 되지 않을 수 있습니다.

기본 복구 방향:

```text
복구 접속 경로 확보
→ 필요 시 방화벽 22 임시 허용
→ 99-b1-1.conf 제거/수정
→ sshd -t
→ daemon-reload
→ ssh.socket/service 적용
→ 22 LISTEN 확인
→ 접속 시험
```

백업 원본은:

```text
/etc/ssh/sshd_config.b1-1.backup
```

에 두었습니다.

이 장과 직접 연결되는 항목:

| ID | 요구사항 | 현재 상태 |

## 19. 이번 단계 기억하기

### 한 문장

> **SSH는 백업하고, 검사하고, 새 포트가 열린 것을 확인한 뒤 전환한다.**

### 핵심어 3개

```text
backup · sshd -t · 20022
```

### 핵심 명령 3개

```bash
sudo sshd -t
sudo sshd -T | grep -E '^(port|permitrootlogin) '
sudo ss -lntp | grep -E ':(22|20022)\b' || true
```

### 내가 설명할 수 있어야 할 것

> 왜 `Port 20022` 한 줄만 바꾸고 바로 끝내면 안 되는가?

답의 핵심은 **설정 문법, systemd/socket 동작, 실제 LISTEN, 방화벽, 새 접속까지 서로 다른 층에서 검증해야 하기 때문**입니다.
